## 背景

SOPBridge 是一个多租户 Web 应用：管理端负责 SOP 的上传、翻译审核和发布，工人端是移动网页，核心能力依赖大模型翻译和 RAG 问答（见 [PRD](../01-prd.md)）。

约束：

- 一个人开发和维护，组件越少越好
- 项目的首要目标是学习，技术要覆盖国内 AI 全栈岗位的常见要求
- AI 相关能力（文档解析、向量化、评估）需要成熟的生态
- 前后端都要有类型检查，接口变更不能悄无声息地出错
- 预算有限，优先选择开源方案和按量付费的服务

## 决策

| 层 | 选择 |
|---|---|
| 前端 | TypeScript + React + Next.js（App Router）+ Tailwind CSS + shadcn/ui |
| 后端 | Python + FastAPI + SQLAlchemy 2 + Alembic + Pydantic v2 |
| 接口契约 | 后端自动生成 OpenAPI 文档，前端据此自动生成 TypeScript 类型 |
| 数据库 | PostgreSQL，向量检索使用 pgvector 扩展 |
| 缓存与后台任务 | Redis；具体用哪个任务队列库，在 Sprint 2 另行决定 |
| 大模型 | 通过 OpenAI 兼容接口调用 DeepSeek / 通义千问，业务代码只依赖自己封装的适配层 |
| 仓库结构 | 单仓库（monorepo）：`apps/web`、`apps/api`、`docs/` |
| 工具链 | 前端用 mise + pnpm，后端用 uv；本地依赖服务用 Docker Compose；CI 用 GitHub Actions |

Next.js 只负责页面渲染和前端路由，业务逻辑全部放在 FastAPI，避免出现两套后端。

## 备选方案与放弃理由

**前端**

- Vue 3 + Nuxt：国内使用也很广，但 React 在大厂和 AI 产品前端中更主流，AI 相关的 UI 组件和示例也更丰富
- Vite + React 单页应用：更简单，但工人端移动页面的首屏性能不如服务端渲染，也学不到 Next.js 的路由和渲染模式

**后端**

- Django + DRF：自带后台管理、ORM 和认证，开发快；但以同步为主，而且框架替你做的事情太多，不利于学习分层设计
- Node.js（NestJS 或 Next.js 全栈）：前后端用同一种语言；但在文档解析、向量化、评估等方面，Python 的 AI 生态更成熟，国内 AI 应用岗也普遍要求 Python
- Go：性能好，但 AI 生态较弱，学习成本高

**接口契约**

- 前后端各自手写类型：容易不一致，接口改了前端也发现不了
- GraphQL：对这个规模来说过重
- tRPC：要求前后端都用 TypeScript

**数据库与向量检索**

- MySQL：国内业务最常用，但向量检索生态不如 pgvector 成熟，通常要另外部署向量数据库；JSON 支持和扩展机制也不如 PostgreSQL
- 独立向量数据库（Milvus、Qdrant）：大规模时性能更好，但多一个组件，就多一份运维工作，还要处理两边的数据一致性。本项目预计文档在千级、文本分块在十万级，pgvector 足够

**大模型接入**

- LangChain 等框架：上手快，但抽象层厚，出问题难排查；为了学习，先手写核心链路，Sprint 5 再评估是否引入
- 自己部署开源模型：需要 GPU，成本高

**仓库结构**

- 前后端分成两个仓库：一个人维护时，改一次接口要在两个仓库分别提 PR；单仓库一个 PR 就能同时改前后端

## 影响

**好处**

- 覆盖国内 AI 全栈岗位的主流技术
- 业务数据和向量都存在同一个数据库里，运维简单
- 类型检查从数据库模型一直贯穿到前端页面

**代价与风险**

- 两种语言、两套工具链，本地环境和 CI 的配置更复杂
- 前后端分开部署，需要处理跨域和登录态（Cookie）的传递
- 数据规模增长到千万级向量时，需要重新评估 pgvector
- 不用 LangChain，意味着要自己写更多代码
- SOP 可能属于客户机密，选择大模型服务商时必须评估其数据使用政策
